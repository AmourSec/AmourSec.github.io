Hexo 博客构建失败时，如何向 Codex 提供有效信息

2026-05-21
  • 教程

Hexo 博客构建失败时，很多人第一反应是把最后一行报错丢给 AI，然后问一句“怎么修”。这通常不够。

对 Codex 来说，真正有用的信息不是“报错了”，而是：

  • 你想完成什么。
  • 你执行了什么命令。
  • 完整错误日志是什么。
  • 最近改过哪些文件。
  • 这个问题能不能稳定复现。
  • 仓库结构和关键配置是什么样。

信息越完整，Codex 越容易直接定位到 _config.yml、主题配置、依赖版本、文章 Front Matter、资源路径或部署配置的问题。

如果你不想从零整理，可以先复制这个页面里的格式，也可以直接使用 Codex 辅助问题排查模板包。

Hexo 问题排查时最该提供的文件

如果你愿意让 Codex 读仓库，优先给这些文件：

类型 文件 用途
站点配置 _config.yml URL、主题、插件、部署、生成规则
主题配置 _config.indigo.yml 或主题 _config.yml 菜单、头像、打赏、评论、统计
文章内容 source/_posts/*.md Front Matter、Markdown、链接、图片
页面内容 source/**/index.md 页面 layout、type、description
依赖信息 package.json、package-lock.json Hexo、插件、渲染器版本
生成结果 public/**/*.html 检查渲染后的页面是否符合预期

如果问题和部署有关，还要提供 GitHub Pages 分支、部署命令和远程仓库配置。但不要把私钥、Token、Cookie 或账号密码发出来。

什么情况下不适合让 Codex 直接修

有些问题不应该直接交给 Codex 自动处理：

  • 你无法提供完整仓库或复现步骤。
  • 错误涉及生产环境、线上付款、用户数据或隐私数据。
  • 你不清楚改动后应该怎么验收。
  • 你希望对方承担正式交付责任或安全责任。

这时更适合先整理问题，而不是马上动代码。

这和博客变现实验有什么关系

这个博客正在做一个很小的实验：不用夸大能力，不承诺正式咨询，只公开一些可以复用的排查模板和文章。如果这些内容帮你节省了时间，可以看 支持与合作；如果你想看这个实验怎么推进，可以看 变现实验。

真正可持续的路径不是“AI 自动接单”，而是先把问题解释清楚，把模板做扎实，让读者能判断它是否真的有用。
