AI Agent 中的 Skills 到底是什么？本质是 Prompt 吗？

2026-04-13
  • 技术深度

前言

如果你最近用过 Claude Desktop、Cursor 或者各类 AI 编程助手，大概率会遇到过 Skills（技能）这个功能。你只需要说一句”帮我分析这段代码的性能瓶颈”，AI 就能自动加载对应的技能，完成从代码分析到优化建议的全流程。

用起来很神奇，但作为技术人员，我们难免会好奇：

Skills 到底是什么？它的本质不就是 Prompt 吗？和 Tools、Plugins 又有什么区别？

这篇文章就来拆解 Skills 的工作原理。不需要你懂 AI 底层架构，只要写过代码、用过命令行，就能看懂。

一、先说结论：本质是 Prompt，但不是”一段话”那么简单

直接回答：Skills 的本质确实是 Prompt，但它是结构化的、可被自动发现和加载的 Prompt 系统。

如果把日常和 AI 对话时写的 Prompt 比作”口头指令”，那么 Skills 就是”操作手册”。口头指令说完就没了，操作手册却可以随时翻阅、按步骤执行。

用一句话概括：

Skill = 描述（让 AI 知道什么时候用）+ 指令（让 AI 知道怎么用）+ 资源（让 AI 有东西可用）

听起来不复杂对吧？但正是这种简单的设计，让它成为了目前 AI Agent 领域最实用的能力扩展方式。

二、Skills 长什么样？

要理解 Skills 的原理，最直接的方式是看看它实际长什么样。

打开 AI 工具的 Skills 目录，你会发现一个”反直觉”的事实：每个 Skill 本质上就是一个 Markdown 文件。

打开其中一个 SKILL.md，内容大致是这样：

没有可执行代码，没有配置文件，没有状态机。就是一段给人看的 Markdown 文档。 但 AI 读完后，就能像一个经验丰富的工程师一样完成代码审查。

这就是 Skills 最有趣的地方：它没有任何运行时引擎，完全依靠大语言模型的理解能力来”执行”。

三、Skills 是怎么工作的？

理解了 Skills 长什么样，接下来看看 AI 是怎么使用它的。整个过程可以分成三步：

第一步：发现——AI 怎么知道有哪些 Skills？

当你启动 AI 工具时，它会在后台扫描 Skills 目录，读取每个 Skill 的描述信息。注意，这里只读取描述，不读取完整内容。

为什么？因为一个 Skill 的完整内容可能有几千字，如果全部加载，会占用大量”上下文窗口”（你可以理解为 AI 的短期记忆空间）。而描述信息通常只有一两句话，足够 AI 判断”这个 Skill 是干什么的”。

这就像你去图书馆，先看书名和简介决定要不要借，而不是一上来就把整本书读完。

第二步：匹配——到底是谁在做决定？

当你输入一个问题后，系统需要判断：该不该用 Skill？用哪个？

这里有一个很多技术人员容易误解的点：这个决定，到底是 App（比如 Cursor、Claude Desktop）里的代码做的，还是背后的大模型做的？

答案是：核心决策是大模型做的，App 只是个“搬运工”和“执行器”。

我们可以把这叫做 “工具搭台，模型唱戏”。

App 做了什么？（搭台）

App 本身不懂你的意图，它只负责把”菜单”端上来。它的工作流程很机械：

  1. 扫描与提取：App 启动时，扫描 Skills 目录，提取每个 Skill 的元数据（名称、一句话描述）。
  2. 注入上下文：App 把这些元数据整理成一段文本，偷偷塞进发给大模型的 System Prompt 中。
    • System Prompt 示例： “你是一个助手。你可以使用以下技能：[技能 A：代码审查…] [技能 B：性能优化…]。当用户请求匹配时，请调用对应技能。”
  3. 执行决定：App 等待大模型返回结果。如果大模型说“我要用技能 A”，App 就去读取技能 A 的完整文件，加载到对话中。

大模型做了什么？（唱戏）

“选择”和“触发时机”的判断，完全是大模型在脑子里完成的。

  1. 理解意图：大模型阅读你的输入（比如“这段代码响应太慢了，帮我看看”）。
  2. 匹配决策：大模型对照 System Prompt 里的技能列表，进行语义匹配。它不需要看到“慢”这个字才触发，它能理解“响应太慢” = “性能问题” = “匹配性能优化技能”。
  3. 输出指令：大模型决定触发后，会输出一个特定的信号（通常是调用一个名为 load_skill 的工具，或者在文本中明确声明）。

为什么要让大模型来做选择？

你可能会问：“为什么 App 不自己用代码判断？比如检测到关键词就触发？”

原因在于 语义理解的鸿沟：

  • App 的规则是死板的：如果 App 用代码写 if "慢" in text: trigger(performance_skill)，那用户说“卡顿”、“延迟高”、“吞吐上不去”时，App 就傻眼了。
  • 大模型的理解是灵活的：大模型受过海量文本训练，它能理解各种同义词、隐喻甚至上下文。
    • 用户： “这个接口怎么跟蜗牛一样。”
    • App： （懵）
    • 大模型： （秒懂） -> 触发“性能分析”Skill。

补充：Skill 太多时怎么办？

如果一个工具有几百个 Skills，全部塞给大模型会撑爆上下文窗口。这时候 App 会介入做初筛：

  1. App 初筛：用向量搜索（Embedding）快速算出和你问题最相似的 Top 5 个 Skills。
  2. LLM 终选：App 只把这 5 个给大模型，由大模型做最终决定。

这样既保证了灵活性，又解决了性能问题。

第三步：加载——AI 怎么”执行” Skill？

一旦 AI 决定使用某个 Skill，它就会读取这个 Skill 的完整内容，把它加入到当前的对话上下文中。

这就是 Skills 的”魔法”所在：它没有任何神秘的执行引擎，只是一段被 AI 阅读并遵循的文本指令。

四、Skills 和 Tools、Plugins 有什么区别？

这是最容易混淆的地方。它们都能扩展 AI 的能力，但底层机制完全不同。

用一个类比来理解

假设你要让一个实习生帮你完成一项工作：

  • Skills 就像给实习生一本操作手册。手册里写了步骤、注意事项、参考资源。实习生看完手册后，自己决定每一步怎么做。

  • Tools 就像给实习生一套专用工具。比如”用这个计算器算数”、”用这个查字典”。实习生需要明确知道什么时候用什么工具，然后动手操作。

  • Plugins 就像给实习生培训新技能。培训完成后，这个技能就成了实习生能力的一部分，不需要再翻手册或拿工具。

具体对比

Skills Tools Plugins
本质 文本指令（Markdown） 函数定义（JSON） 代码扩展
执行方式 AI 阅读理解后自主执行 AI 调用，程序执行 加载后成为 AI 的一部分
适合场景 复杂工作流、多步骤任务 单一明确的操作 框架级功能扩展
修改成本 低（改文本就行） 中（需要改代码） 高（需要开发测试）

它们怎么配合工作？

实际使用中，这三者经常配合：

Skills 负责”整体策略”，Tools 负责”具体操作”。

五、为什么这种”简单”的设计有效？

一段 Markdown 文本就能让 AI 完成复杂任务，听起来有点不可思议。但这背后有几个关键原因：

1. 大语言模型的”上下文学习”能力

这是最核心的原因。现代大语言模型有一个重要特性：当你给它提供指令和示例时，它不需要重新训练，就能学会执行新任务。

这在技术上叫 In-Context Learning（上下文学习）。你给它的 Prompt 越清晰、结构越好，它执行得就越准确。

Skills 本质上就是把这种能力工程化了——把好的 Prompt 模板化、可复用化。

2. 分步引导的力量

好的 Skill 不会只说”帮我优化代码”，而是会拆解成具体步骤：

这种分步指令利用了大语言模型的”思维链”效应：AI 在生成每一步输出时，前面的内容会成为后续推理的基础，形成自我强化的逻辑链。

3. 角色设定的作用

很多 Skill 开头会写”你是一个资深性能优化专家”。这不是废话，而是一种经过验证的技巧：角色设定能激活大语言模型在预训练阶段学到的相关知识。

实验表明，同样的问题，加上角色设定后，回答质量会有明显提升。

六、Skills 的局限性

Skills 虽然好用，但不是银弹。了解它的局限性，才能更好地使用它。

上下文窗口有限

每个 Skill 的内容都会占用 AI 的”记忆空间”。如果同时激活多个 Skill，或者 Skill 内容太长，AI 可能就没有足够的空间来处理你的实际问题了。

应对方法：Skill 内容要精简，只保留核心指令；把参考资料放在外部，按需加载。

AI 可能”忘记”指令

在多轮对话中，尤其是对话很长的时候，AI 可能会逐渐偏离 Skill 中定义的步骤。这不是 bug，而是大语言模型的特性——它更关注最近的对话内容。

应对方法：在关键步骤前提醒 AI 回顾 Skill 定义；把长 Skill 拆成多个短 Skill。

执行顺序不绝对可靠

AI 是概率模型，不是程序解释器。它不保证严格按照 Skill 中的步骤顺序执行，可能会跳过某步，或者打乱顺序。

应对方法：用”必须”、”禁止”等强约束词；对于顺序要求严格的场景，考虑用代码实现工作流。

调试不太方便

当 Skill 执行结果不符合预期时，很难快速定位问题：是 Skill 描述不够清楚？AI 理解有偏差？还是某个步骤本身就有问题？

应对方法：记录完整的对话过程；给 Skill 添加明确的验收标准。

七、写好一个 Skill 的建议

基于对多个 AI 工具中 Skills 的分析，总结几条实用建议：

结构要清晰

不需要花哨的格式，但结构要一目了然。

一个 Skill 只做一件事

不要试图把代码审查、性能优化、测试生成塞进一个 Skill 里。保持聚焦，AI 执行起来更准确。

用强约束词

“建议检查安全问题”和”必须检查以下安全问题”，效果完全不同。对于关键步骤，用”必须”、”禁止”、”第一步”这样的词。

八、总结

回到最初的问题：Skills 的本质是 Prompt 吗？

是的。 Skills 没有任何神秘的执行引擎，它就是一段结构化的 Prompt 文本。

但不只是 Prompt。 它把 Prompt 工程化了——有描述让 AI 知道什么时候用，有指令让 AI 知道怎么用，有资源让 AI 有东西可用。

Skills 代表了一个有趣的方向：用自然语言定义行为，用大语言模型作为执行引擎。 它简单到令人惊讶——就是一个 Markdown 文件——但效果却出奇地好。

当然，它也有明显的局限：上下文有限、指令可能遗忘、执行顺序不绝对可靠。对于顺序要求严格、容错率低的场景，传统的代码实现仍然是更好的选择。

但对于那些”需要灵活性、允许一定容错、依赖领域知识”的任务，Skills 提供了一种轻量级、易维护、快速迭代的解决方案。

下次你在使用 AI 工具时，不妨打开 Skills 目录看看。你会发现，那些让 AI 变得”聪明”的秘诀，其实就写在一个个朴素的 Markdown 文件里。
