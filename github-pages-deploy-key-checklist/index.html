GitHub Pages 部署失败：SSH、Branch、Deploy Key 怎么查

一个面向 Hexo/GitHub Pages 部署失败的安全排查清单，覆盖本地构建、git remote、SSH、branch、deploy key、Pages 设置和 GitHub Actions 权限。

Hexo 本地能构建，不代表一定能部署到 GitHub Pages。

部署失败通常不是一个点的问题，而是一条链路里某一段断了：本地 build、Git remote、SSH 认证、目标 branch、GitHub Pages 发布来源、deploy key 写权限、GitHub Actions workflow 权限，都可能导致类似的失败现象。

这份清单只做安全排查，不让你公开粘贴密钥，不自动改 GitHub 设置，也不执行部署。

先把链路拆开

排查部署问题时，建议按这个顺序看：

  1. 本地构建是否成功。
  2. 当前仓库 remote 是否指向正确 GitHub 仓库。
  3. 当前 branch 和部署目标 branch 是否一致。
  4. SSH 是否能认证到 GitHub。
  5. 如果使用 deploy key，公钥是否加在正确仓库，并且需要写入时是否有写权限。
  6. GitHub Pages 发布来源是 branch 还是 GitHub Actions。
  7. 如果使用 Actions，workflow 是否有 Pages 部署所需权限。

GitHub 官方文档也强调：GitHub Pages 可以从指定 branch 发布，也可以通过 GitHub Actions workflow 发布；自定义 Pages workflow 通常需要 pages: write 和 id-token: write 这类权限。deploy key 则是授予单个仓库访问能力的 SSH key。参考：配置 GitHub Pages 发布来源、使用自定义 GitHub Pages workflow、管理 deploy keys。

非破坏性命令清单

下面这些命令只用于查看状态或本地构建，不会改远程仓库。

如果 ssh -T 显示成功认证，但 git push 仍失败，下一步通常不是继续试错，而是确认 remote URL、deploy key 写权限、目标 branch 和 GitHub Pages source 是否一致。

不要公开粘贴什么

排查部署失败时，不要把这些内容发到公开页面、评论区或 AI 工具里：

  • 私钥文件内容，例如 ~/.ssh/id_rsa、~/.ssh/github_blog。
  • GitHub token、classic PAT、fine-grained token、Actions secret。
  • deploy key 私钥或完整配置截图。
  • 未脱敏的完整 Actions 日志。
  • 私有仓库 URL、内部组织名、邮箱、用户名、本地绝对路径。
  • .env、生产配置、服务器 IP、后台地址、部署脚本里的密钥。

可以公开提供的是：脱敏后的错误关键词、remote 形态、目标 branch、使用 branch 发布还是 Actions 发布、执行过的非破坏性命令。

这类排查的边界

可以本地做：

  • 读配置文件和 workflow 草稿。
  • 看 git remote -v、git branch -vv、git status --short。
  • 运行 npm run build。
  • 整理脱敏后的错误和支持请求。

必须用户确认：

  • 登录 GitHub。
  • 新增、删除或替换 SSH key / deploy key。
  • 修改 GitHub Pages 发布来源。
  • 修改 GitHub Actions 权限。
  • 执行 hexo deploy、git push 或任何远程写入动作。

不应该做：

  • 让别人贴私钥、token 或完整 secret。
  • 为了部署成功而绕过账号、权限或组织规则。
  • 在不理解目标 branch 的情况下反复推送。
  • 把部署问题包装成“保证修复”的服务。
