技术问题收集清单模板：字段为什么这样设计

技术问题收集清单模板：字段为什么这样设计

一个解释技术问题 intake 模板字段设计的指南，说明目标、环境、命令、错误、复现步骤、已尝试动作和敏感信息移除为什么必要。

很多排查请求不是问题太难，而是输入太模糊。

“帮我看看报错”这句话很自然，但对 Codex 或任何协助者来说，它缺少目标、环境、命令、上下文和验收方式。结果通常是先来回追问，或者根据错误片段走错方向。

一份好的技术问题 intake 模板，不是为了让提问者多填表，而是为了把最容易缺失、最影响判断的信息提前放到同一处。

模糊请求为什么浪费时间

模糊请求会带来三个问题。

第一，无法判断目标。构建失败、部署失败、页面空白、样式错乱，背后想达成的目标可能完全不同。

第二，无法复现。没有环境、命令和最近改动，Codex 只能猜测是依赖、配置、路径、权限、内容格式还是部署平台问题。

第三，容易越界。如果没有限制条件和敏感信息声明，协助者可能会要求不该提供的日志、私钥、token、客户数据或生产凭据。

推荐字段

字段 为什么重要 简短示例
goal 定义最终要达成什么，避免只围绕报错本身打转 让 Hexo 本地执行 npm run build 成功
environment 版本、系统和工具链会直接影响错误判断 macOS, Node 20, npm, Hexo 8
repository_or_page_link 帮助聚焦阅读范围；没有公开链接时也要说明 公开仓库链接 / 页面链接 / 暂无公开链接
command_run 没有命令就无法判断执行路径和入口 npm run build
expected_result 区分真正错误、配置差异和误解 应生成 public/ 目录
actual_result 描述实际发生了什么，提供判断入口 构建中断，提示 YAMLException
error_excerpt 关键错误片段比完整噪音更有用，也更容易脱敏 YAMLException: duplicated mapping key
reproduction_steps 判断问题是否稳定复现，以及从哪里开始复现 clone 后 install，再运行 build
already_tried 避免重复建议，也能暴露错误方向 已试过 hexo clean 和删除 public/
recent_changes 很多问题来自最近新增文章、依赖或配置 昨天新增了一个页面和一篇文章
sensitive_information_removed 强制先脱敏，避免把不该发的内容贴出来 已移除 token、邮箱、本地用户名
success_criteria 让协助结果可验收，而不是无限排查 构建成功，且文章页能打开

这组字段可以覆盖大多数小范围技术问题：Hexo 构建、静态站点配置、Node 脚本、Markdown 页面、主题配置和轻量工具原型。

可复制 Markdown Intake 模板

和现有工具怎么配合

如果你只是想整理一份可复制文本，可以直接用 支持请求格式化器。它在浏览器本地运行，不发送、不保存。

如果你要发给站长或自己留作记录，可以从 支持请求 Intake 模板 复制完整中文模板。

如果你想把这类字段变成长期可复用的工作流，可以看 Codex Workflow Template Pack 和 Codex 辅助问题排查模板包。

如果你要直接交给 Codex 排查，可以先看 如何把排查请求写成 Codex 能执行的任务，里面有更完整的处理流程提示词。

不要放进模板的内容

技术 intake 的目标是帮助判断问题，不是收集越多信息越好。下面这些内容不要直接贴：

  • API token、cookie、SSH key、私钥、密码、session。
  • 生产数据库地址、生产凭据、后台登录信息。
  • 客户资料、订单、手机号、身份证件、支付信息。
  • 公司内部完整日志、内部域名、私有路径和未脱敏截图。
  • 医疗、法律、财务、身份、合同或其他受监管数据。
  • 任何你没有权利分享的第三方代码、资料或文件。

如果问题离不开这些信息，应该先停止公开求助，改用合适的内部流程或专业渠道。

什么时候不用填这么多

如果只是问一个概念问题，或者请 Codex 解释一段公开代码，可以简化。

但一旦你希望别人复现、修改、排查、判断原因或给出可执行步骤，就应该至少提供目标、环境、命令、预期结果、实际结果和已移除敏感信息。
