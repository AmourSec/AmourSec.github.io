如何把排查请求写成 Codex 能执行的任务

一个面向 Codex 调试请求的结构指南，说明如何提供目标、上下文、环境、命令、预期结果、实际结果、已尝试步骤和边界。

Codex 能帮你排查问题，但它不应该靠猜。

很多低效请求看起来像这样：

这句话的问题不是“不能问”，而是 Codex 没法判断目标、环境、命令、最近变更、验收方式和不能碰的边界。它只能先反问，或者在错误方向上做无用尝试。

为什么模糊请求浪费时间

调试不是只看最后一行报错。一个看起来相同的错误，可能来自不同原因：

  • 依赖版本不一致。
  • 命令在错误目录执行。
  • 配置文件语法不合法。
  • 文章 Front Matter 写坏。
  • 本地环境和部署环境不同。
  • 沙箱权限、端口或文件访问限制。

如果请求里缺少上下文，Codex 很可能先走错方向。

一份可执行请求的结构

字段 要回答的问题 为什么重要
目标 你最终想完成什么？ 判断修复是否达成
上下文 这是哪个项目、页面、文章或工具？ 避免误把问题当成别的场景
链接 / 文件 哪些公开链接或文件相关？ 帮 Codex 聚焦阅读范围
环境 OS、Node/Python、包管理器、框架、部署平台是什么？ 很多错误和版本/平台有关
命令 你执行了什么命令？ 没有命令就无法复现路径
预期结果 本来应该发生什么？ 区分 bug、误解和配置差异
实际结果 实际发生了什么？ 错误现象和日志入口
已尝试步骤 你已经试过什么？ 避免重复无效建议
限制条件 哪些文件、依赖、部署动作不能动？ 防止越界修改
已移除敏感信息 确认哪些内容已脱敏？ 避免泄露 token、私钥、客户数据
希望输出 你要排查步骤、补丁、解释还是提示词？ 控制结果格式

如果不想手工整理，可以先用 支持请求格式化器 生成一份文本。

什么时候应该先停下来

如果问题涉及下面情况，不适合直接让 Codex 继续：

  • 生产事故、线上恢复、紧急修复。
  • 支付、订单、用户隐私、受监管数据。
  • 私有账号登录、KYC、后台操作、平台申诉。
  • 正式安全审计、漏洞报告、法律、税务、财务、医疗判断。
  • 需要保证结果、响应时限、合同或长期售后。

这些情况需要先确认责任边界和合适的专业渠道。

和现有工具怎么配合

  1. 先用 支持请求格式化器 整理字段。
  2. 如果是 Hexo 日志，先用 Hexo 报错信息整理器 提取关键信息。
  3. 如果看到 YAMLException 或 Front Matter 文件名，再看 Hexo Front Matter / YAML 报错排查清单。
  4. 如果仍然需要人工判断，再看 支持请求 Intake 模板 和 支持与合作。
